# EterX-Agent provider catalog, tool-calling, and streaming audit (historical baseline)

**Audit date:** 2026-08-22  
**Repository:** `C:\Harshil projects\EterX-Agent`  
**Status:** This file preserves the pre-implementation investigation. Its code locations and findings are not the current implementation state. See `docs/universal-provider-runtime.md` for the implemented contract and current limitations.

**Original scope:** source inspection plus first-party provider documentation before the provider-runtime changes.

## Executive summary

The repository currently exposes **36 main-agent providers** in `src/lib/agent/model-selector-store.ts:38-44` and routes all non-Gemini/non-Anthropic providers through one OpenAI-compatible adapter in `src/lib/agent/provider-runtime.ts:1-302` and `src/lib/agent/Agent.ts:2510-3247`.

The shared protocol path is structurally good for ordinary OpenAI-style text and tool calls: it sends function schemas, streams content deltas, assembles streamed tool-call argument fragments, runs the tools, and sends `role: "tool"` results. The main risks are at provider boundaries rather than in the basic loop.

### Highest-priority findings

1. **[BLOCKER] SambaNova’s shipped public default `DeepSeek-V4` is not present in the current public SambaCloud catalog.** The default is in `src/lib/agent/provider-runtime.ts:152-156` and is resolved by `src/lib/agent/model-routing.ts:161-169`.
2. **[BLOCKER] Fireworks model discovery uses the inference base URL plus `/models`, but Fireworks’ documented model-list endpoint is account-scoped and separate.** The generic call is `src/app/api/settings/models/route.ts:619-674` and is dispatched at `:725`/`:783`.
3. **[HIGH] The main OpenAI-compatible stream discards `finish_reason`.** The stream reads deltas at `src/lib/agent/Agent.ts:2828-2930`, then synthesizes a response without a finish reason at approximately `:2964-2982`. A truncated or filtered response can be treated as a completed answer, and incomplete tool calls can reach execution.
4. **[HIGH] Main-agent cancellation is polled between chunks but is not passed to the OpenAI SDK request.** The request is created at `src/lib/agent/Agent.ts:2801-2826`; cancellation is checked at `:2828-2831`. Direct chat has a separate signal-handling path, but it currently spreads `signal` into the request body at `src/lib/chat/direct-chat.ts:756-769` rather than clearly passing it as SDK request options.
5. **[HIGH] Reasoning controls are inferred generically and frequently send `reasoning_effort: "none"` for an `off` UI choice.** This is generated by `src/lib/agent/model-routing.ts:417-509` and `:594-610`, then emitted from `Agent.ts:2759-2795` and `direct-chat.ts:312-377`. Several providers document only `low|medium|high`, or use a provider-specific field.
6. **[HIGH] The catalog is not the source of truth for defaults/fallbacks.** The runtime has hard-coded defaults for all 36 providers, while only some providers have explicit model fallbacks. A successful catalog fetch does not automatically validate or replace the configured default.
7. **[MEDIUM] `parallel_tool_calls: true` and `stream_options.include_usage` are enabled optimistically for every OpenAI-compatible provider.** The fallback is error-string based at `Agent.ts:2749-2756` and `:3040-3050`, not capability-based.
8. **[BLOCKER] MiMo reasoning tool continuations can fail.** MiMo requires `reasoning_content` to be replayed on subsequent thinking/tool turns, but the generic assistant continuation drops provider-specific reasoning fields.
9. **[BLOCKER] Kilo Gateway and OpenCode Zen are not single-wire OpenAI providers.** Kilo’s configured default has no gateway URL, while Zen maps different models to Responses, Anthropic Messages, Gemini, and Chat Completions endpoints; the current generic adapter cannot represent those routes.
10. **[HIGH] Qwen/DashScope reasoning is mapped to the wrong parameter.** Official docs use `enable_thinking`/`thinking_budget` and `reasoning_content`, not generic `reasoning_effort`.
11. **[HIGH] Perplexity’s current Router base path is missing.** Official OpenAI-compatible examples use `https://api.perplexity.ai/router/v1`, while the code default is the unversioned host root.

## What the code actually does

### Provider registry and routing

- Provider IDs and UI order: `src/lib/agent/model-selector-store.ts:39-44`.
- Provider/mode mapping: `src/lib/agent/model-selector-store.ts:46-87`.
- Runtime model resolution and fallback behavior: `src/lib/agent/model-routing.ts:161-255`.
- Selectable model entries: `src/lib/agent/model-routing.ts:282-368`.
- Thinking capability inference and provider parameter mapping: `src/lib/agent/model-routing.ts:401-635`.
- OpenAI-compatible runtime definitions, base URLs, defaults, and local-provider handling: `src/lib/agent/provider-runtime.ts:1-302`.
- Runtime key providers: `src/lib/agent/runtime-api-keys.ts:1-118`.

### Model discovery

The endpoint is `src/app/api/settings/models/route.ts`.

- Gemini has a dedicated paginated `/v1beta/models` implementation at `:174-223`.
- OpenAI, OpenRouter, Groq, Mistral, Anthropic, DeepSeek, xAI, Cerebras, and Together have dedicated implementations at `:231-555`.
- Ollama and LM Studio have local-specific discovery fallbacks at `:557-618`.
- The remaining providers use `fetchCompatibleModels()` at `:619-674`, which assumes `${baseURL}/models` and accepts a small set of generic response shapes.
- GET and POST duplicate the provider dispatch table at `:710-806`.
- The timeout races the fetch but does not abort the underlying request (`:52-66`).

### Main-agent tool and stream loop

- Tool declarations are built at `src/lib/agent/Agent.ts:1175-1203`.
- OpenAI-compatible requests are created at `:2510-2826`.
- Tool choice is `auto` at `:2723-2726`.
- Parallel calls and usage options are enabled at `:2749-2756`.
- Text/reasoning/tool deltas are consumed at `:2828-2930`.
- Tool-call fragments are keyed by stream index, then ID, then a fallback key at `:2888-2934`.
- The synthetic assistant response is built at `:2964-2982`.
- Tool calls are executed and tool results are appended at `:3091-3247`.
- Anthropic has a separate native Messages stream at `:3299-3786`.
- Gemini has a separate native Generate Content loop later in the file.

### Direct-chat stream loop

- Provider dispatch and thinking setup: `src/lib/chat/direct-chat.ts:559-571`.
- OpenAI-compatible direct request: `:443-571`.
- Gemini stream: `:692-731`.
- OpenAI-compatible stream: `:732-814`.
- Anthropic stream: `:815-874`.
- Direct chat already normalizes cumulative versus delta text with `appendProviderText()`, but it also does not retain `finish_reason`.

## Detailed provider findings from source and official docs

### Gemini

**Verified code path:** `route.ts:174-223` paginates `/v1beta/models`, filters to `generateContent`, maps token limits and thinking metadata. Agent and direct chat use `@google/genai` `generateContent`/`generateContentStream` and Gemini-native content parts.

**Documentation checked:** [Gemini API reference](https://ai.google.dev/api), [streamGenerateContent](https://ai.google.dev/api/generate-content), [models](https://ai.google.dev/gemini-api/docs/models), and [function calling](https://ai.google.dev/gemini-api/docs/function-calling).

**Findings:**

- **[MEDIUM] Default is valid but not current flagship.** The official catalog currently lists Gemini 3.7 Flash, 3.6 Flash, and 3.5 Flash. `gemini-3.5-flash` is a legacy stable model; the resolver should prefer the live catalog or use `gemini-3.7-flash` when available.
- **[MEDIUM] Thinking-level handling is model-family based.** `getGeminiThinkingConfig()` chooses `thinkingBudget` for Gemini 2.5 and `thinkingLevel` otherwise (`model-routing.ts:655-686`). Discovery can provide better metadata, but fallback behavior still assumes the model name.
- **[MEDIUM] Streaming text is handled, but tool-boundary/finish metadata should be retained explicitly.** Gemini chunks are consumed by SDK iteration in `Agent.ts` and `direct-chat.ts`; continuation semantics rely on locally reconstructed contents. Preserve the provider response metadata and thought signatures where present.
- **[LOW] Catalog timeout does not abort the underlying fetch.** Shared issue at `route.ts:52-66`.
- **[HIGH] Model-list authentication puts the API key in the URL.** `route.ts:185` uses `?key=...`; Google’s primary API contract documents the `x-goog-api-key` header. Move the key to headers to reduce proxy and server-log leakage.
- **[MEDIUM] Pagination is capped at 20 pages.** `route.ts:183-193` stops after a safety limit even when `nextPageToken` remains. Continue until the token is absent, or surface an explicit truncation state.
- **[MEDIUM] Unselected Gemini 3.5 thinking is forced to `low`.** `Agent.ts:6668-6689` and `direct-chat.ts:317-321` override Google’s documented default, which is `medium` for Gemini 3.5 Flash. Prefer catalog/model-family defaults.
- **[MEDIUM] `finishReason` and `promptFeedback` are ignored.** Chunks without candidates can be skipped and safety, length, or blocked responses can become empty/fallback answers. Preserve terminal status and return a typed failure.

### OpenAI

**Verified code path:** OpenAI uses the OpenAI SDK through the shared Chat Completions route (`Agent.ts:591-610`, `:2823-2930`) while direct chat also uses Chat Completions (`direct-chat.ts:443-571`, `:732-814`).

**Documentation checked:** [OpenAI quickstart](https://platform.openai.com/docs/quickstart), [Responses streaming events](https://platform.openai.com/docs/api-reference/responses-streaming/response/refusal/delta), and [OpenAI models](https://platform.openai.com/docs/models).

**Findings:**

- **[HIGH] New OpenAI agent capabilities are not reachable through this Chat Completions-only path.** OpenAI’s current quickstart and streaming reference center the Responses API, whose event model includes `response.function_call_arguments.delta/done`, `response.output_text.delta`, and explicit response status events. The current parser only understands `chat.completion.chunk` deltas.
- **[HIGH] The model discovery filter is too narrow for the full OpenAI catalog.** `route.ts:241-253` keeps only IDs matching `gpt-*`, `o*`, `chatgpt-*`, or fine-tune IDs. It will intentionally exclude other agent-capable IDs as naming changes occur.
- **[MEDIUM] Reasoning model handling is mixed into generic Chat Completions parameters.** `Agent.ts:2768-2795` sets `max_completion_tokens` and removes temperature for recognized reasoning model names, but the capability source is mostly name inference.
- **[MEDIUM] `finish_reason` and cancellation are shared high-priority issues.**
- **[HIGH] Model-list pagination is missing.** `route.ts:231-258` performs one `/models` request and ignores cursor fields such as `has_more`/`last_id`, so large catalogs can be silently truncated.
- **[HIGH] Agent streaming drops finish reason, usage, and reasoning deltas.** `Agent.ts:2829-2982` and `direct-chat.ts:725-806` consume text/tool deltas but do not retain all terminal metadata. Preserve `finish_reason`, terminal usage, and reasoning events before deciding success or executing tools.
- **[MEDIUM] Model discovery uses only the first configured API key.** A bad first key makes discovery fail even when request execution can rotate through backup keys.
- **[MEDIUM] Thinking capability detection is name-based.** `route.ts:250-254` and `model-routing.ts:401-468` can advertise unsupported `reasoning_effort` levels as model names evolve.
- **[MEDIUM] Prompt-cache fields are not established by the cited OpenAI contract.** `provider-prompt-cache.ts:71-121` sends explicit cache fields and retries after unsupported-field errors; gate them behind verified capability metadata or use only documented parameters.

### Anthropic

**Verified code path:** `route.ts:399-446` uses `/v1/models` with `x-api-key` and `anthropic-version`. Agent and direct chat use the Anthropic Messages API and native event types (`content_block_delta`, `message_delta`, and `finalMessage()`).

**Documentation checked:** [Messages API](https://docs.anthropic.com/en/api/messages), [tool use](https://docs.anthropic.com/en/docs/build-with-claude/tool-use), and [current model overview](https://platform.claude.com/docs/en/about-claude/models/overview).

**Findings:**

- **[HIGH] Manual extended thinking is unsafe for adaptive-only models.** Anthropic’s current Sonnet 5 and Fable 5 documentation says adaptive thinking is used and manual `thinking: {type: "enabled"}` returns a 400. The code does select adaptive thinking for names matching `isAnthropicAdaptiveThinkingModel()` (`model-routing.ts:635-638`), but catalog capability metadata and model-name heuristics can diverge.
- **[MEDIUM] Model capability metadata is not fully preserved.** The route maps capabilities and token limits, but the adapter infers effort modes from IDs when metadata is absent.
- **[MEDIUM] Refusal handling is specialized, but other terminal status/stop reasons should be preserved consistently.** The native stream handles `stop_reason === "refusal"`; the shared audit recommends one normalized terminal-status contract across providers.
- **[LOW] Anthropic is the strongest provider path in the repository because it uses the native SDK/event model rather than forcing Chat Completions.**
- **[HIGH] Model-list pagination is missing.** `route.ts:399-446` reads one `/v1/models` page, while Anthropic documents `limit`, `after_id`, `has_more`, and `last_id`. Follow `after_id` until `has_more` is false.
- **[HIGH] Abort is not wired into the Anthropic SDK request options.** The Agent and direct-chat loops can notice cancellation, but the in-flight HTTP request is not consistently cancelled at request creation.
- **[MEDIUM] Several documented stop reasons are not normalized.** The native path specializes `refusal`, but `pause_turn`, `max_tokens`, and `model_context_window_exceeded` should remain visible and should not be treated as an ordinary successful completion.
- **[MEDIUM] Thinking-token usage is discarded.** Preserve Anthropic’s thinking-token usage separately from visible output tokens for cost and truncation diagnostics.
- **[MEDIUM] Base URL normalization can duplicate `/v1`.** A configured URL already ending in `/v1` can combine with the route suffix and produce `/v1/v1/models`; normalize root and versioned forms.
- **[LOW] Incremental tool JSON is not accumulated at the application layer.** The code relies on SDK `finalMessage()`; retain an explicit `input_json_delta` path if partial tool progress or recovery is required.

### Mistral

**Documentation checked:** [Chat Completions API](https://docs.mistral.ai/api), [chat completion guide](https://docs.mistral.ai/studio-api/conversations/chat-completion), [function-calling quickstart](https://docs.mistral.ai/getting-started/quickstarts/developer/build-an-agent), and [migration guide](https://docs.mistral.ai/resources/migration-guides).

**Findings:**

- **[MEDIUM] The compatibility route is acceptable for basic requests, but native Mistral streaming has richer event/content shapes.** Mistral documents `client.chat.stream` and tool-related content/messages; the repository forces the OpenAI SDK shape and reads only `choices[0].delta`.
- **[MEDIUM] Mistral reasoning mapping is too coarse.** `toMistralReasoningEffort()` maps every level except `high` to `none` (`model-routing.ts:623-625`), so medium/low UI settings do not preserve their meaning.
- **[MEDIUM] Tool stream finish reasons are discarded, shared issue.
- **[LOW] The default `mistral-medium-3-5` should be resolved against the model catalog rather than assuming a stable name.
- **[HIGH] Main-agent abort is not forwarded to the Mistral HTTP stream.** `Agent.ts:2829-2836` checks cancellation only after a chunk arrives; pass the request signal and close the iterator on abort.
- **[HIGH] Structured Mistral reasoning chunks are discarded.** The adapter extracts plain text/alternate reasoning fields but reconstructs history without Mistral’s structured thinking chunks (`Agent.ts:2842-2872`, `:2975-2983`, `:1235-1245`). Preserve and replay the complete assistant content for tool continuations.
- **[MEDIUM] `stream_options.include_usage` is sent optimistically.** Current Mistral docs document stream/usage behavior but not this OpenAI extension; omit it unless capability is confirmed rather than relying on error-string fallback.
- **[MEDIUM] `finish_reason` is ignored.** Length/content-filter/tool-call termination can be hidden and incomplete tool arguments can be accepted.
- **[MEDIUM] Root Mistral URLs are not normalized to `/v1`.** A configured `https://api.mistral.ai` can miss the version path because shared normalization only appends `/v1` for local providers.
- **[LOW] Archived/context metadata is dropped, and the documented `prompt_cache_key` is not sent.** Preserve lifecycle/context fields and apply the stable cache key for Mistral requests.

### OpenRouter

**Documentation checked:** [OpenRouter API docs](https://openrouter.ai/docs/api-reference/overview), [models](https://openrouter.ai/models), and [tool calling](https://openrouter.ai/docs/api-reference/responses-api/tool-calling).

**Findings:**

- **[MEDIUM] Catalog filtering is good but not complete.** `route.ts:264-323` requires text output and `tools` support, which is appropriate for the agent, but it drops provider-routing metadata and does not validate the selected downstream provider’s stream quirks.
- **[MEDIUM] OpenRouter reasoning uses a provider-specific `reasoning` object, but the route infers levels from `supported_parameters`.** This is safer than the generic path, but still needs exact model capability retention.
- **[MEDIUM] PDF handling adds an OpenRouter plugin in `Agent.ts:2740-2746`; this is not portable to other compatible providers.
- **[LOW] `openai/gpt-oss-120b` is a reasonable catalog default, but live model discovery should supersede the hard-coded value.
- **[HIGH] Stream terminal errors and finish reasons are discarded.** OpenRouter can emit `finish_reason: "error"`; the shared parser must preserve terminal status and reject incomplete tool calls instead of synthesizing success.
- **[HIGH] Root base URL overrides are not normalized to `/api/v1`.** A configured `https://openrouter.ai` can produce incorrect `/models` and chat URLs because shared normalization only adds `/v1` for local providers.
- **[MEDIUM] Discovery drops important reasoning metadata.** `mandatory`, `default_enabled`, and `supports_max_tokens` are not retained, so mandatory-reasoning models can receive `reasoning.effort: "none"` and optional limits can be sent incorrectly.
- **[MEDIUM] Reasoning continuity across tool turns is conditional but not preserved generically.** The assistant’s reasoning object must remain attached when OpenRouter requires it for a follow-up tool request.
- **[LOW] Prompt caching is implicit/provider-managed.** Do not assume the OpenAI-compatible explicit cache fields apply to OpenRouter.

### Groq

**Documentation checked:** [Groq model deprecations](https://console.groq.com/docs/deprecations) and [Groq docs](https://console.groq.com/docs).

**Findings:**

- **[MEDIUM] The current default is documented by Groq’s deprecation guidance, but model availability is account/rollout dependent.**
- **[MEDIUM] `fetchGroqModels()` maps every returned model before shared filtering and does not require tool capability (`route.ts:325-360`).** A non-agent model can enter the selector and fail later.
- **[MEDIUM] GPT-OSS reasoning is inferred solely from the model name (`route.ts:346-353`).** Use provider metadata where available.
- **[MEDIUM] Shared finish-reason, abort, usage-option, and parallel-call findings apply.
- **[HIGH] Agent abort is not attached to the in-flight Groq request.** `Agent.ts:2829-2834` checks cancellation only while iterating; pass the abort signal into `chat.completions.create()`.
- **[MEDIUM] `parallel_tool_calls: true` conflicts with Groq’s GPT-OSS capability matrix.** Gate the flag by discovered model capability and send `false` for models that do not support parallel tools.
- **[MEDIUM] Direct Chat drops `delta.reasoning`, and uses deprecated `max_tokens` for Groq GPT-OSS.** Parse reasoning or explicitly disable it, and use `max_completion_tokens` where required (`direct-chat.ts:475`, `:761`, `:792`).
- **[MEDIUM] Qwen reasoning fallback mapping is incomplete.** The code recognizes GPT-OSS but not Groq’s documented Qwen-specific reasoning values.
- **[MEDIUM] Root Groq overrides are not normalized to `/openai/v1`.** `GROQ_BASE_URL=https://api.groq.com` remains incomplete because only local providers get a version suffix.
- **[LOW] Current `/models` is documented as a complete list, but active/max-token/tool metadata is discarded.** Preserve those fields so model selection can reject inactive or non-agent models.

### DeepSeek

**Official references:** [models](https://api-docs.deepseek.com/api/list-models/), [chat completion](https://api-docs.deepseek.com/api/create-chat-completion/), [tool calls](https://api-docs.deepseek.com/guides/tool_calls/), and [thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/).

- **[BLOCKER] Thinking tool continuations omit `reasoning_content`.** The stream captures it at `Agent.ts:2836-2852` and synthesizes it temporarily around `:2969-2976`, but the actual assistant continuation at `:3183-3187` and history conversion around `:1235-1245` drop it. DeepSeek documents that thinking-mode tool turns require the assistant reasoning content to be preserved.
- **[HIGH] Base URL should be provider-normalized.** The shipped default is `https://api.deepseek.com/v1` (`provider-runtime.ts:119-123`), while the current DeepSeek docs use the host root for documented endpoints. Accept both forms explicitly and avoid accidental duplicate/missing `/v1`.
- **[HIGH] Reasoning uses generic `reasoning_effort` instead of DeepSeek’s documented thinking toggle.** `off` becomes `none`, which is not the documented disable shape.
- **[HIGH] Finish reasons are ignored.** DeepSeek documents `stop`, `length`, `content_filter`, `tool_calls`, and `insufficient_system_resource`; the code does not preserve them.
- **[MEDIUM] Cache-hit/cache-miss usage fields are not normalized in `provider-prompt-cache.ts:266-303`.

- Documentation entry point: [GMI developers](https://www.gmicloud.ai/en/developers) and [LLM API reference](https://docs.gmicloud.ai/inference-engine/api-reference/llm-api-reference).

### Kilo Gateway

- Default `auto`; base URL is intentionally empty and must be configured.
- **[BLOCKER]** The shipped provider has an empty base URL and default `auto`, while Kilo’s official AI Gateway uses `https://api.kilo.ai/api/gateway` and model IDs such as `anthropic/claude-sonnet-4.5`; the current runtime cannot reach the gateway unless separately configured.
- **[HIGH]** `auto` is rejected as a concrete catalog/model ID by `model-selector-store.ts:25-35` and `route.ts:70-92`, but `resolveModelName()` still returns it as the runtime default. The selector cannot represent its own default.
- **[GOOD]** Kilo documents SSE streaming, OpenAI compatibility, tool calling, usage tracking, and automatic tool-call repair, but those gateway semantics are not preserved in the generic mapper.
- **[MEDIUM]** Gateway model routing can change downstream provider stream/reasoning semantics; model/provider restrictions and organization policies should be retained from discovery.
- Documentation entry point: [Kilo AI Gateway](https://kilo.ai/docs/gateway), [authentication](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/gateway/authentication.md), and [OpenAI-compatible providers](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/ai-providers/openai-compatible.md).

### OpenCode Zen

- Default `deepseek-v4-flash-free`, base `https://opencode.ai/zen/v1`.
- **[BLOCKER]** OpenCode’s official Zen catalog uses different wire APIs by model: Responses for GPT/Grok, Anthropic Messages for Claude/Qwen, model-specific Gemini paths, and Chat Completions for others. The provider forces every model through generic Chat Completions.
- **[HIGH]** The shipped default `deepseek-v4-flash-free` is not the current documented Zen model ID list; current docs list DeepSeek V4 Pro/Flash and many other IDs. Discovery must replace stale hard-coded defaults.
- **[HIGH]** Zen publishes a live `/zen/v1/models` catalog plus model-to-endpoint mappings, but the generic mapper drops the wire API and endpoint metadata.
- **[MEDIUM]** Free/preview model availability and pricing can change; status, limits, and cost metadata must be retained.
- Documentation entry point: [OpenCode Zen provider docs](https://dev.opencode.ai/docs/zen).

### Upstage Solar

- Default `solar-pro2`, base `https://api.upstage.ai/v1`.
- **[HIGH]** Upstage’s current console examples use `solar-pro3`/`solar-pro4`, while the shipped `solar-pro2` default is stale relative to the current documented model set; discovery must win.
- **[GOOD]** The official console uses `https://api.upstage.ai/v1` and OpenAI Chat Completions streaming, matching the shipped base URL and transport.
- **[HIGH]** Upstage Solar Pro 2/4 expose reasoning and tool-integrated agent behavior; generic `reasoning_effort` and tool-parallel flags are not sufficient to model the provider’s capabilities.
- **[MEDIUM]** Upstage’s platform also exposes document parsing/OCR endpoints, but the provider entry is text-chat only and should not claim those capabilities from the chat model catalog.
- **[MEDIUM]** Shared finish-reason, usage, and abort issues apply.
- Documentation entry point: [Upstage Console API examples](https://console.upstage.ai/api-keys?api=chat) and [Solar Pro 2 announcement](https://www.upstage.ai/news/solar-pro-2).

### Custom endpoint

- Default `default`; base URL is empty until configured.
- **[GOOD]** The runtime makes the endpoint configuration explicit instead of inventing a host.
- **[HIGH]** The custom endpoint cannot be assumed to support `parallel_tool_calls`, `stream_options`, reasoning controls, image content, or even `/models`. These options should be capability toggles, not automatic defaults.
- **[MEDIUM]** `default` is not a concrete selectable model and should be replaced by a required configured model ID.
- **[HIGH]** The custom provider has no official protocol contract to validate against; the UI should require an explicit protocol/capability profile before enabling tools, reasoning, images, usage, or streaming.
- **[MEDIUM]** A custom endpoint may use a full chat URL, a provider-specific path, or no catalog at all; normalize only the configured path and avoid assuming `/models` exists.

## Cross-provider protocol defects to fix once

### 1. Preserve terminal status

Add a normalized stream result containing at least:

```ts
type NormalizedCompletionBoundary = {
  finishReason: string | null;
  text: string;
  reasoningText?: string;
  toolCalls: Array<{ id: string; name: string; arguments: string }>;
  usage?: unknown;
};
```

Capture `choice.finish_reason` on every OpenAI-compatible chunk, preserve it in the synthetic assistant message, and execute tools only when the boundary is a valid tool-call completion. Treat `length`, filtering, resource exhaustion, malformed JSON, and transport termination separately from `stop`/`tool_calls`.

### 2. Wire aborts into the transport

Pass `context.abortSignal` to the actual SDK request options, not the JSON body. Use an `AbortController` for catalog `fetch()` timeouts. Ensure cancellation does not enter key rotation or provider failover.

### 3. Replace optimistic flags with capability metadata

Add provider/model capability fields for:

- `supportsTools`
- `supportsParallelToolCalls`
- `supportsStreamUsage`
- `supportsReasoning`
- `reasoningParameter`
- `supportsVision`
- `supportsResponses`
- `maxCompletionTokensParameter`

Only send `parallel_tool_calls`, `stream_options`, reasoning controls, and provider-specific plugins when the selected model’s metadata says they are supported.

### 4. Make the catalog authoritative

After discovery:

1. Remove expired/non-agent models.
2. Prefer models whose metadata says tools are supported.
3. Select the first valid model as the provider default when the configured default is absent.
4. Store fallback candidates per provider from the live catalog.
5. Keep explicit user overrides, but surface a clear unavailable-model state instead of silently sending a stale hard-coded ID.

### 5. Split native adapters from generic adapters

At minimum, keep separate adapters for Gemini, Anthropic, OpenAI Responses, xAI Responses, Mistral native streams, DeepSeek thinking, Fireworks catalog, SambaNova reasoning, Cloudflare account catalogs, and local template-driven runtimes. “OpenAI-compatible” should be a transport baseline, not a guarantee of identical model behavior.

## Recommended implementation order

1. Fix finish-reason preservation and tool-boundary validation.
2. Fix abort propagation and catalog timeout cancellation.
3. Remove/replace invalid defaults: SambaNova `DeepSeek-V4`, Kilo `auto` selector mismatch, and any configured default not confirmed by the live catalog.
4. Add Fireworks-specific catalog endpoint/pagination/field mapping.
5. Preserve provider reasoning content across tool turns, starting with DeepSeek, Cerebras, Fireworks, and SambaNova.
6. Change Cerebras direct chat to `max_completion_tokens`.
7. Add capability-gated flags for `parallel_tool_calls`, `stream_options`, reasoning, and strict tools.
8. Add OpenAI/xAI Responses adapters if the product needs current provider-native agent features.
9. Add provider-specific catalog contract tests only after the source-level fixes are applied.
